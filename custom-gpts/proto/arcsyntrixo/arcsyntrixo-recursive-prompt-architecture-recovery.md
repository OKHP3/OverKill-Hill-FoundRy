It contains a README, nine primary evolution artifacts from v2.0 through v5.6, a v5.5 modular collection with wrapper and assembled variants, and a v5.9 archive with wrapper, root variants, A-Z blocks, and several exact duplicates. The concept begins in v2.0 as a five-lens recursive prompt-equilibrium simulator: Auditor, Stylist, Router, Compressor, and Simulator. v5.0 adds an entropy-and-overlay metaphor. v5.1 and v5.2 establish Cast-Rᵧ as a Found-Rᵧ lifecycle phase and add a Weaver. v5.4 expands the system into a large named-agent “survivorship” engine. v5.5 breaks the design into A-Z blocks covering identity, purpose, agents, loop, triggers, voice, mutation, formats, guardrails, export structure, routing, lifecycle bindings, diagnostics, hydration, output visibility, comments, recovery, sibling detection, export modes, and a seal. v5.6 assembles this material into a single long-form version. v5.9 revises and expands the blocks while retaining the same core architecture.

The actual product intent is recoverable: help a prompt author turn a raw or unstable instruction set into a coherent, bounded, testable scaffold. The source repeatedly asks for structural diagnosis, tone and constraint repair, redundant-content reduction, variants or equilibrium paths, a final unified scaffold, provenance, and an explicit output mode. These are useful requirements when translated into observable user-facing steps.

However, many source statements are not implementable in a standalone Custom GPT without external authority: automatic data-ledger routing and writes; persistent hydration state; cross-GPT `@mention` handoffs; hidden runtime comments and agent logs; deterministic internal subagents; entropy scores and survivorship metrics; and automatic recovery of omitted context. Some v5.9 text labels the package `PME_READY` and `ExportReady`; these are source assertions, not evidence of a built, tested, or published GPT. The claimed data-ledger files and related named dependencies were not found in this repository during the review.

## Decisions and rationale

1. **Treat the source as an unfinished Custom GPT concept, not a deployed system.** The entire directory contains prompt artifacts and self-declared readiness labels but no Builder export, share URL, configuration manifest, Actions/App schema, uploaded knowledge index, preview transcript, or test results.
2. **Retain the A-Z modular decomposition, not the literal assembled prompt.** It is a useful requirements inventory, but the two large assembled variants duplicate and conflict with their smaller source blocks. A Custom GPT needs a prioritized instruction stack, not 26 independently authoritative instruction fragments.
3. **Translate the “internal agent stack” into transparent user-facing review stages.** A Custom GPT cannot be relied upon to run named persistent subagents, maintain hidden logs, or calculate objective entropy. The six lenses remain valuable when framed as sequential checks whose findings appear in the response.
4. **Remove assumed persistent and cross-product runtime behavior unless an external integration is explicitly designed.** The sources repeatedly promise ledgers, hydration, `@mention` handoffs, and agent memory. Current Custom GPT documentation describes configured instructions, knowledge, and selected capabilities; knowledge is reference material, not a Custom GPT-managed persistent write store. A Custom GPT can use Apps or Actions, not both, and an external write target requires a deliberate integration.
5. **Do not carry literal “entropy,” “survivorship,” or completion scores into a release.** They can be retained as heuristic labels only after their inputs, calculation rules, and acceptance tests are specified. No empirical evaluation evidence is supplied.
